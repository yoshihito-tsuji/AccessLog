# 指示: 2/28 スパイク再発の根本原因を確定し、ロジックを防御的に修正してください

## 背景（2026-03-02時点）
- 2/24・2/27 スパイクは削除で解消したが、2/28 が +4 → +238 に変化。
- 2/28 のバージョン別増分が 2/16 とほぼ一致（PoPuP Win v1.2.0 のみ +4）。
- これは「単なる実DL増加」ではなく、データ選別/キー処理の不整合を疑う状況。

## 重要方針
- **これ以上、日付一括削除は行わないこと。**
- まず原因確定（証跡付き）→ 次に修正実装の順で進めること。

## タスク1: デプロイ不一致の即時判定（仮説Aの確定/棄却）
1. Apps Script `doGet` に `type=meta` を追加し、以下をJSON返却:
   - `scriptVersion`（固定文字列。例: `"1.2.1-debug-2026-03-02"`）
   - `generatedAt`（サーバ時刻）
2. `curl "${API_URL}?type=meta"` で取得し、期待バージョンが返るか確認。
3. 返らない場合は「編集対象と公開URLが不一致」または「デプロイ未更新」と判断し、正しいプロジェクト/デプロイに揃える。

## タスク2: DailyData 生データの法医学調査（仮説Bの確定）
Apps Script に調査関数 `inspectDailyDataSnapshots(startDate, endDate)` を追加し、
`2026-02-14`〜`2026-03-02` を対象に以下を出力してください。

1. 日付ごとのタイムスタンプ一覧（件数付き）
2. 各タイムスタンプの総行数
3. 各タイムスタンプでの「app×version」件数
4. タグの生文字列差異検出（trim前後比較、不可視文字の有無）
   - `tagRaw`
   - `tagTrimmed`
   - `tagNormalized`（NFKC + trim）
5. 2/28 について「複数スナップショットがあるか」「どのスナップショットが不完全か」を明示

## タスク3: ロジック修正（再発防止）
`getTimelineData()` を次の方針に更新してください。

1. **キー正規化**
   - `versionName = normalizeKey(tag)` を使用
   - `normalizeKey()` は `String(value).normalize('NFKC').trim()` を最低限実施

2. **日次データの選別方式を変更**
   - 現在の「日付ごとに最新タイムスタンプ1つだけ採用」をやめる
   - 日付内の全タイムスタンプを集計し、`app×version` ごとに **その日の最大累積値** を採用
   - （目的）不完全スナップショット1件に引きずられないようにする

3. **増分計算**
   - 既存の `maxSeenCount` を維持（後退値による二重計上抑止）
   - `effectivePrev = max(prevCount, maxSeenCount)` を継続

## タスク4: 検証
1. `testIncrementBaseline()` を拡張し、次を追加:
   - 同日複数タイムスタンプ（片方が不完全）でも正しい増分になるケース
   - タグの空白/全角差異を正規化して同一バージョン扱いになるケース
2. `diagnose.sh --breakdown` または同等手順で検証し、以下を提示:
   - 2/16, 2/24, 2/27, 2/28 の日次増分
   - 30日合計の修正前後差分
   - 2/28 が +4 に戻るか（または説明可能な値か）

## 完了条件
- 仮説A/Bの採否を証跡つきで確定。
- 2/28スパイク再発の再現条件を説明できる。
- 修正後のロジックで「削除なしでも」過大計上が抑止される。

- 4) 残リスクと追加提案

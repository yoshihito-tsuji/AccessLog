# ダッシュボード集計データ乱れ（234 DL の三重計上）の調査・修正依頼

## 0. 背景・経緯

2026-02-17 に Codex 指示のもと「ベースライン考慮の初日スパイク修正」を実施し、
テスト（8 passed）・デプロイ・コミット（`0582a4a`）まで完了しました。

しかし 2026-03-01 のセッションで、**新たなデータ乱れ**が発見されました。
今回の問題は「初日スパイク（ベースライン未考慮）」とは別の現象です。

---

## 1. 問題の概要

Apps Script API（`type=timeline&days=60`）を解析したところ、
**2026-02-16・2026-02-23・2026-02-26 に全く同一の増分値（234 DL）が計上されています。**

```
2026-02-16: +234 DL  GaQ(Mac)=41, GaQ(Win)=50, PoPuP(Mac)=30, PoPuP(Win)=113 ← 正常？
2026-02-17〜22: 0 DL（データなし）
2026-02-23: +234 DL  GaQ(Mac)=41, GaQ(Win)=50, PoPuP(Mac)=30, PoPuP(Win)=113 ← ！
2026-02-24〜25: 0 DL（データなし）
2026-02-26: +234 DL  GaQ(Mac)=41, GaQ(Win)=50, PoPuP(Mac)=30, PoPuP(Win)=113 ← ！
2026-02-27: 0 DL
2026-02-28: +4 DL  PoPuP(Win)=4
2026-03-01: 0 DL（本日）
```

3 日とも **アプリ別の内訳が完全一致**しており、偶然ではなく構造的な問題です。

### 影響（PDF スクリーンショットより、2026/3/1 21:24 時点・30日間表示）

| アプリ | 表示値 |
|---|---|
| GaQ (Mac) | 124 |
| GaQ (Windows) | 150 |
| PoPuP (Mac) | 91 |
| PoPuP (Windows) | 349 |
| **合計** | **714** |

3 回のうち 1 回は正規なので、過大計上は **234 × 2 = 468 DL** です。
本来の 30 日間合計は **714 - 468 = 246 DL 前後** と推測されます。

## 3. 原因仮説

### 仮説A（最有力）：Google Sheets DailyData に同一累積値が 3 回記録された

DailyData シートに 2026-02-16・2026-02-23・2026-02-26 で
同一の累積スナップショットが記録されており、
ベースライン修正後の Apps Script が各エントリを独立した「前日比差分」として計算しています。

Apps Script の差分計算ロジック：
```javascript
// 2026-02-16（初出）: prevCount = ベースライン（N） → currentCount = N + 234 → 増分 +234
// 2026-02-23（重複）: ???
// 2026-02-26（重複）: ???
```

**疑問点**：2026-02-16 のエントリが DailyData に存在するなら、
2026-02-23 の prevCount は N+234 になるはずなので、増分は 0 になるはずです。
しかし実際は 234 になっており、この矛盾の原因が不明です。

考えられる可能性：
- (a) DailyData の 2026-02-16 行が実際は存在せず、どこか別のエントリが「初出」になっている
- (b) Apps Script の差分計算ロジックが特定条件でリセットされている
- (c) バージョン別に処理するため、一部バージョンだけが 2026-02-16 に出現し、
     残りのバージョンが 2026-02-23、2026-02-26 に「初出」として出現している
- (d) upload_to_sheets.py の重複チェックが機能せず、2026-02-23・2026-02-26 に
     「2026-02-16 と異なる記録日時で同一累積値」が書き込まれた

### 仮説B：ベースライン修正後のロジックに特定条件下でのバグが残っている

2026-02-17 の修正では、「表示期間外の最新累積値をベースラインとして取得」する仕組みを
実装しました。しかし、以下の条件が重なると再スパイクが起きる可能性があります：

- データ欠損日（2026-02-17〜22）のあと
- 同一累積値のエントリが複数日に記録されている

この場合、欠損後のエントリが「バージョンの新規出現」として扱われ、
ベースライン=0 で差分計算される可能性があります。

---

## 4. 確認が必要な事項

以下を Codex に確認・調査をお願いします：

### 4.1 Google Sheets DailyData の実際のデータ

以下の日付範囲の DailyData を確認してください：
- 2026-02-14 〜 2026-02-28
- 各行の「記録日時」「アセット名」「ダウンロード数（累積）」

特に：
- 2026-02-16・2026-02-23・2026-02-26 の各行が実際に存在するか
- 各行の累積値が本当に同一か
- 「バージョン」列の値が一致しているか

### 4.2 Apps Script の差分計算ロジックの再確認

現在の `config/google_apps_script.js` の `getTimelineData()` 関数において、
以下のケースでどう動作するかを確認してください：

- **ケースX**: 同一バージョンの累積値が同一日に複数エントリある場合
- **ケースY**: 2026-02-16 にエントリがあり、2026-02-23 に同一累積値が来た場合
- **ケースZ**: データ欠損後（2026-02-17〜22 が空）に同一累積値が来た場合

### 4.3 upload_to_sheets.py の重複チェック

現在の重複チェックは `_filter_rows_by_date()` 関数（[scripts/upload_to_sheets.py:300-306](../scripts/upload_to_sheets.py)）で実装されており、
「記録日時フィールドが `YYYY-MM-DD` で始まる全行を削除してから再挿入する」冪等性保証の仕組みです。
つまり **同日の全データを一括置換** する実装になっています。

この仕組みであれば「同じ日に再実行しても重複しない」は保証されていますが、
以下の点は防止できていません：

- **異なる日付で同一累積値が記録された場合**（例: 2026-02-23 のスクリプト実行が 2026-02-16 のデータをアップロードした）
- **track_downloads.sh が古い CSV を参照してアップロードした場合**

この観点から、問題発生時にどの日付の CSV が実際にアップロードされたかをご確認ください。

## 5. Claude Code からの修正方針案

### 案1（推奨）：DailyData の重複行を削除

2026-02-23 と 2026-02-26 の重複エントリを Google Sheets から削除します。

```
メリット: 根本解決。Apps Script の修正不要。
デメリット: 手動作業またはスクリプトで Sheets 操作が必要（credentials.json 要）。
```

### 案2：Apps Script の差分計算を「連続する同値をスキップ」するよう修正

同一バージョンで直前の累積値と同じ場合は増分 0 とする。

```
メリット: データが汚染されていても正しく計算できる。
デメリット: Apps Script の修正が必要。
         「真の増分 0」と「重複エントリ」を区別できない。
```

### 案3：案1 + 案2 の組み合わせ

Sheets のクリーンアップ（案1）を実施後、
今後の同様の問題に備えて Apps Script に防御的ロジック（案2）を追加する。

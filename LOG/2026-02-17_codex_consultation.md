# ダッシュボード日次増分計算のバグ報告と修正案の相談

## 1. 問題の概要

2026-02-17朝、Yoshihitoさんよりダッシュボード（90日間表示）に**異常なスパイク**が表示されている報告がありました。具体的には、期間内の合計が GaQ (Mac): 82, GaQ (Windows): 100, PoPuP (Mac): 63, PoPuP (Windows): 229, 合計: 474 と表示されていますが、実際にはこの期間に大量DLは発生していません。

## 2. 調査結果

### 2.1 ローカルCSV（正常）
- 2/10〜2/16の日次CSV累積値は**全期間でほぼ同一**（変動はPoPuP v1.2.0が77→78の+1のみ）
- GitHub APIの現在値ともCSVが完全一致
- **CSV記録側にバグなし**

### 2.2 根本原因：`config/google_apps_script.js` の差分計算ロジック（236-253行目）

```javascript
// バージョンごとに日次増分を計算
versionNames.forEach(versionName => {
    const dailyData = [];
    let prevCount = 0;  // ★ ここが問題

    dateList.forEach(date => {
        if (appData[appName][date]?.[versionName] !== undefined) {
            const currentCount = appData[appName][date][versionName];
            const increment = Math.max(0, currentCount - prevCount);
            dailyData.push(increment);
            prevCount = currentCount;
        } else {
            dailyData.push(0);
        }
    });

    versions[versionName] = dailyData;
});
```

**問題点**: `prevCount = 0` で初期化しているため、**表示期間内で最初にデータが出現した日に、累積値の全量が「日次増分」として計上される**。

### 2.3 具体例（90日間表示の場合）
- 期間起点: 2025-11-20頃
- 初日のPoPuP v1.2.0 `PoPuP_Portable_v1.2.0.zip` 累積: 78
- → 差分: 78 - 0 = **78** が「その日のDL数」として表示される
- 同様に、GaQ v1.1.1-mac 累積14 → **14**、GaQ windows-v1.1.1 累積10 → **10** など
- これが全バージョンで発生し、合計474という大きな数字になる

### 2.4 影響
- **7日間/30日間表示**: データが安定期のため差分はほぼ0で問題が目立たない
- **90日間/180日間/365日間表示**: 期間起点がデータ記録開始日に近づくほど、初日スパイクが顕著に現れる
- ダッシュボード上部のカウンターカードの合計値も影響を受ける（本来0に近いはずの増分合計が474になっている）

## 3. 修正案の提案

### 案A: 表示期間より前のデータから prevCount を初期化する（推奨）

表示期間の起点より前の最新データを取得して、`prevCount` の初期値とする方式。

```
メリット:
- 期間内の「純粋な増分」のみが表示される
- 表示期間を変えても正確な差分が計算される
- 既存データの修正不要

デメリット:
- 全データを走査する必要があるため、処理が若干複雑化
- 対象期間より前にデータがない場合（記録開始日が期間内の場合）は、
  初日の累積値がそのまま増分として表示される（完全には避けられない）
```

**実装イメージ**:
1. 全レコードから、対象期間の起点日より前の最新データを各バージョンごとに取得
2. それを `prevCount` の初期値として使用
3. 対象期間より前にデータがないバージョンについては、最初のデータ出現日の累積値をそのまま増分とする（＝真に「新規」）

### 案B: 初日の増分を0として扱う

表示期間内で最初にデータが出現した日の増分を0とする方式。

```
メリット:
- 実装がシンプル
- スパイクが完全に消える

デメリット:
- 初日に本当にDLがあった場合もカウントされない
- 7日間/30日間に切り替えた際に初日のDLが消える
```

### 案C: 表示期間を「データ記録開始日以降」に制限する

データが存在しない期間を表示しない方式。

```
メリット:
- 現行ロジックを変更不要

デメリット:
- 根本解決にならない（記録開始日の初日スパイクは残る）
- ユーザーが期間を自由に選べなくなる
```

## 4. Claude Code としての推奨

**案Aを推奨**します。理由:
1. データの正確性が最も高い
2. ユーザーがどの期間を選んでも正しい増分が表示される
3. 過去のDECISIONS（2026-01-11）でも「期間内の増分合計」が設計意図であることが確認されており、その設計意図に最も忠実

## 5. 追加の再発防止策（提案）

1. **ダッシュボードに注釈追加**: 「表示値は選択期間内の日次増分合計です」等の説明
2. **diagnose.sh の検証項目追加**: Apps Script APIのレスポンスとCSV差分の整合性チェック
3. **テスト関数の追加**: Apps Script内にセルフテスト用関数を設け、差分計算が正しいことを検証

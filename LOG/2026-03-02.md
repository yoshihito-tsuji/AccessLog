#### Task 2: 二重実行の原因調査

**launchd 登録状況確認:**

```
launchctl list | grep com.releases.download-tracker
→ 登録済み（このマシンが 23:59 に実行）
```

**plist 設定 (`StartCalendarInterval`):**

```xml
<key>StartCalendarInterval</key>
<dict>
    <key>Hour</key><integer>23</integer>
    <key>Minute</key><integer>59</integer>
</dict>
```

**二重実行メカニズム（仮説）:**

macOS の `StartCalendarInterval` は、スリープ中に予定時刻を過ぎた場合、
次回起動時にジョブをキューして即時実行する。
マシンが 23:59 付近でスリープ/ウェイク を繰り返した場合、
launchd が同一スケジュールを 2 回発火させることがある。
→ `track_downloads.sh` が 2 プロセス起動 → 各々 `upload_to_sheets.py` を呼び出し → 二重 append

tracker.log の各日エントリが 1 件のみ（`実行日時: 2026-XX-XX 23:59:XX`）なのは、
stdout（tracker.log）は各実行で別プロセスが上書きするためと考えられる。
tracker_error.log は `mode='a'`（追記）のため両プロセスの出力が重なる。

**注**: `flock` が macOS 非対応のため PID ロックファイル方式を採用

**PID ロックの動作:**

```bash
LOCK_FILE="${LOG_DIR}/.track_downloads.lock"
# 実行中プロセスが存在するならスキップ
if kill -0 "${EXISTING_PID}"; then
    log_error "二重起動をスキップします (PID: ${EXISTING_PID})"
    exit 0
fi
echo $$ > "${LOCK_FILE}"
trap "rm -f '${LOCK_FILE}'" EXIT INT TERM
```

**`_filter_rows_by_date` 修正後:**

```python
# '2026-02-28' → '2026/2/28' に変換（gspread Date型対応）
target_slash = f"{dt.year}/{dt.month}/{dt.day}"
matches = cell.startswith(target_date) or cell.startswith(target_slash)
```
